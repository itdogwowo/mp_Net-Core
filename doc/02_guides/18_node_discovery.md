## 0. 先用一句話講完

```
遙控器：廣播「你是誰？」→ 每台節點各自回「我是 0x0002，我叫 xxx」
        → 遙控器記住它 → 指定「以後你回話回給我」→ 開始操作
```

**就這四步。** 但每一步都有踩過的坑，這份文件把坑一起寫進去。

---

## 1. 為什麼「發現」在 ESP-NOW 上是個問題

一般匯流排（I2C、RS485）可以**逐位址掃**：位址是 0x00～0xFE 的數字空間，
一個一個問就好。

**ESP-NOW 不行。** 它的位址是 **MAC（6 bytes）** —— 那不是一個可以列舉的
數值空間，你沒辦法「從 00:00:00:00:00:00 掃到 FF:FF:FF:FF:FF:FF」。

所以「被發現」只有兩條路：

| 方法 | 誰發起 | 什麼時候用 |
|---|---|---|
| **廣播點名** `0x100D` | **想找人的那一方** | 遙控器主動按「掃描」 |
| **自我公告** `0x1002` | **想被找到的那一方** | 節點開機時廣播一次 |

> ★ 這兩條是**互補**的，不是二選一。
> 節點開機時公告一次 → 已經在線的遙控器馬上看到它。
> 遙控器後來才開機 → 它反過來廣播點名。
> **任一方晚到都不會漏掉對方。**

---

## 2. 四個指令的角色

| 指令 | 名字 | 誰發 | 發給誰 | 幹什麼 |
|---|---|---|---|---|
| `0x1002` | `SLAVE_ANNOUNCE` | 節點 | **廣播** | 「我開機了，我是誰」|
| `0x100D` | `IDENTIFY_REQ` | 遙控器 | **廣播** | 「你是誰？」|
| `0x100E` | `IDENTIFY_RSP` | 節點 | **單播**回問的人 | 「我是 0x0002，slave_id=…，ip=…」|
| `0x1016` | `SET_MASTER` | 遙控器 | 單播 | 「以後你回話回給我」＝**方向** |

### ★ 最重要的一條設計原則：**身分 ≠ 方向**

- **身分**（你是誰）→ `0x100D` / `0x100E`
- **方向**（我聽誰的）→ **只有 `0x1016` 一個寫入者**

這兩件事**刻意不共用一個變數**。為什麼？看下一節。

---

## 3. 一個真實踩過的坑：掃描不該順便認主人

### 症狀

第二台遙控器只要按一下「掃描」，射程內**所有**節點就全部改認它當主人
—— 第一台遙控器完全不知道，操作到一半就失效了。

### 原因

`0x100E` 這封回信需要一個**目的位址**（NC4 標頭裡的 `addr`）。
早期的 `_reply()` **只能從 `bus.master_cid` 拿位址**，所以為了回這一封信，
`on_identify_req` 只好先把 `reply_cid` 塞進 `master_cid`。

**結果：一次點名 = 一次認主。**

### 後果（四個）

1. **無聲搶奪**：任何人按掃描都能搶走全部節點
2. 狀態自相矛盾：`master_cid` 有值，但 `role` 還是 `None`
3. 只改記憶體、不發布 → 用 `0x1101` 查會查到**舊值**
4. 不落盤 → 重開機還原，這次開機期間的歸屬與 btree 不一致

### 修法

`_reply()` 補上 `addr` 參數 —— 「**這一封**回信寄哪」變成單次指定，
不再是全域狀態：

```python
_reply(ctx, CMD_IDENTIFY_RSP, {...}, addr=reply_cid)   # 只影響這一封
```

> ★ 教訓：**「少一個參數」的變通，代價通常是污染一個全域狀態。**
> 當你發現自己要「先改 A 才能做 B」，那通常表示缺的不是時序，是參數。

## 4. 完整流程（從開機到能操作）

```
【節點開機】
  節點 ──廣播 0x1002 SLAVE_ANNOUNCE{slave_id, pixel_count, hw_version}──▶ 所有人
                                                       （只有一次，不週期）
【遙控器那邊】
  收到 → PeerRegistry 登記（學到 MAC）→ 清單出現一列
  ⚠️ 但**公告不帶 cid** → 這一列還沒有 cid

【遙控器按「掃描」】（使用者主動）
  遙控器 ──廣播 0x100D IDENTIFY_REQ{reply_cid=我的cid, timeout_ms=500}──▶ 所有人
  每個節點：各自隨機延遲 [0, 500]ms 後
  節點 ──單播 0x100E IDENTIFY_RSP{cid, slave_id, ip}──▶ 遙控器
  遙控器：登記/更新 → 這一列**補上 cid**

【遙控器選一台按「綁定」】
  遙控器 ──單播 0x1016 SET_MASTER{master_cid=我的cid}──▶ 那台節點
  遙控器本地：記進 @node.targets（active）

【開始操作】
  遙控器 ──單播 0x3101 MODE_LIST_QUERY──▶ 節點
  節點 ──單播 0x3102 MODE_LIST_RSP──▶ 遙控器
  （細節 0x3107 / 0x3108 逐一補）
```

### 為什麼「掃描」是必要的，不能只靠公告

因為**公告不帶 cid**。

| 來源 | 學到 MAC | 學到 cid |
|---|---|---|
| `0x1002` 公告 | ✅ | ❌ |
| `0x100D` 點名的回覆 `0x100E` | ✅ | ✅ |

而**綁定需要 cid**（`0x1016` 要用它當定址鍵）。
所以流程上：**掃描 → 才有 cid → 才能綁定**。

> ⚠️ 週期公告關掉之後（2026-10 定案），**`0x100E` 是 cid 的唯一來源**。
> 「按了綁定沒反應」通常就是這條：那台還沒回過掃描。

## 5. `0x100D` 其實是兩種模式

`0x100D` **不是一個指令**，是兩個，用 `reply_cid` 區分 —— 行為完全不同：

| `reply_cid` | 模式 | 行為 | 誰用 |
|---|---|---|---|
| **具體 cid** | **定向點名** | **每次都回** | **面板（遙控器）** |
| `0xFFFF` | **廣播回覆** | 同一個問的人**只回第一次** | 還沒有 cid 的問方 |
| `0xFFFF` + `force=1` | 強制 | 忽略上面的紀錄，重回 | 要強制重新自我介紹 |

### 為什麼「廣播回覆」要節流

它是**全專案唯一會讓射頻上每一台同時回話**的指令。第一次是必要的
（不自我介紹就沒人知道我），但**同一個人再問一次不會得到新資訊** ——
只是把同一次碰撞再付一次代價。

### ★★ 狀態的鍵是「問的人的 MAC」，不是一個 bool

這是最容易寫錯的地方。用 bool 會出現：

> 第一台遙控器掃過之後 bool = True
> → **第二台比較晚開機的遙控器永遠收不到回覆**

也就是「**我開機不等於他開機**」那個症狀。

所以狀態記的是「**我對誰回過了**」：

```python
_FF_REPLIED = {}        # 問的人的 MAC(hex) -> 最後回覆的 ticks_ms
_FF_KEEP = 4            # 只記最近 4 個人，不讓它無限長
```

換一個人問 = 一個沒見過的人 → **一定要回**。

> ★ 一般化的教訓：**節流/去重的鍵要選「對方是誰」，不是「有沒有做過」。**
> 用 bool 就是把「對 A 做過」錯誤地推廣成「對所有人都做過」。

## 6. 抖動（jitter）：為什麼回覆要隨機延遲

```
節點 ──廣播 0x100D──▶ 射程內 8 台節點
                       ↓ 如果不抖動
      8 台在**同一瞬間**回話 → 空中硬碰撞 → 整批掉
```

所以 `0x100D` 帶一個 `timeout_ms`（**抖動視窗**），各節點抽一個
`[0, timeout_ms]` 的隨機延遲，把「同時」攤成「序列」。

| `timeout_ms` | 行為 |
|---|---|
| `0` 或缺席 | 不抖動、立即回（**舊客戶端的行為**）|
| `> 0` | 隨機延遲 `[0, timeout_ms]` 後才回 |

**為什麼只有 `0x100D` 要抖動**：全專案「廣播出去、N 台回話」的只有它。
其餘廣播（`0x1401/0x1501/0x1502/0x3105/0x3106`）都是**單向**的，沒人回話。

★ 判準不是「`addr` 是不是 `0xFFFF`」，而是「**有沒有 N 台會回**」——
靠「寫在這個 handler 裡」來保證，不需要執行期判斷。

★ **非阻塞**：handler 只**排程**、不等待。用 `time.sleep_ms()` 會卡住
core0 的解碼鏈與 UI，而且停擺期間 `poll()` 不跑 → 幀只能堆在驅動層而掉落。

真機實測（視窗 500ms）：`395 / 332 / 119 ms`。

## 7. 面板上看到什麼（顏色 = 關係狀態）

清單每一列的顏色回答的是「**我跟它是什麼關係**」，**不是**「它多久沒講話」：

| 顏色 | 意義 | 什麼時候變 |
|---|---|---|
| 🟢 綠 | 我認的目標（在 `@node.targets`）| 按「綁定」|
| 🟡 琥珀 | 這次掃描有回（`age_ms <= since`）| 按「掃描」|
| 🔴 紅 | **掃描過了，它沒回** | 按「掃描」後約 0.5 秒 |
| ⚪ 灰 | 還沒按過掃描（我還沒問過）| 開機 |

**選中那一列**：淺藍底 + **永遠保留狀態色**（不能用深藍底＋白字，
那樣狀態色會被蓋掉）。

### ★ 為什麼不用「時間衰減」（綠→黃→紅）

因為 **`age` 變大只代表「對端沒有再講話」，不代表它離線**。
用時間上色會變成「按掃描 → 綠 → 幾秒後自己變琥珀 → 再變紅」，
看的人只會困惑：我又沒做什麼，它為什麼變了？

而且「掃描成功」建立的是一個**關係**（我知道你是誰、你的 MAC），
那個關係不會因為 10 秒過去就失效。

## 8. 壞掉的時候怎麼查

### 8.1 三層分開看

發現流程會壞在三層，**先確定是哪一層**，不要一起猜：

```
① 射頻層   兩台在不在同一個頻道？（ch 要一樣，ESP-NOW 才有機會收到）
② 指令層   0x100D 有沒有送出去？對方有沒有收到？有沒有回 0x100E？
③ UI/狀態層 收到了，但沒有顯示 / 顯示成錯的顏色？
```

### 8.2 對照表

| 症狀 | 最可能的原因 |
|---|---|
| 按掃描，**全部**節點都沒反應 | 頻道不同 / 對方沒開 / 自己的 `NowBus.connected = False` |
| 按掃描，**有些**節點沒反應 | 空中碰撞（再按一次）／那台真的不在 |
| 清單有那一列，但**綁定沒反應** | 那台**還沒有 cid**（只學過公告，沒回過 `0x100E`）|
| 綁定成功但**沒有回覆** | **`0x1016` 本來就沒有 ACK**（見下）|
| 顏色不對 | 那是 UI 層，看第 7 節的狀態表 |

### 8.3 `0x1016` **無 ACK**，這是刻意的

`SET_MASTER` 送出去之後**不會有回應**。要確認對方收到了，得**另外查**：

```
送 0x1016  →  再用 0x1101 STATUS_GET 問它「你的 master_cid 是誰」
```

真機實測：`0x1016` 送 5 次會掉 1 次（無 ACK、無重送）。
所以「按了綁定好像沒用」有兩種可能：**(a) 根本沒送到**、**(b) 送到了但沒有回音**。
分辨方法就是上面那個 `0x1101` 回查。

## 9. 除錯方法論（這一節跟協議無關，但最值錢）

這一輪修了四個「**看起來成功、其實沒有**」的失敗。它們的共同點是
**驗證本身是壞的**，而不是程式是壞的。

### 9.1 新增一個判斷依據時，**先拿已知的陽性/陰性對照組驗它**

真實案例：寫了一個「這個字在字型裡有沒有 glyph」的稽核，跑出來

```
CHECKED 640
MISSING 0
✅ 沒有缺字
```

看起來是好消息。**實際上 640 個字一個都沒量到** ——
`font.get_glyph_width(ch)` 對**每一個**字元都丟 `TypeError`（簽名不對），
而結果解析器又只認 `MISSING`、沒印 `ERRORS`。

修好之後的對照組：

```python
# 陽性：一定要回 True
'A' / '1' / 空白 / 一個確定存在的字
# 陰性：一定要回 False
U+E000（私用區）/ U+10FFFD（未分配）/ emoji
```

> **陰性若回 True，這個 oracle 就不能用。**

### 9.2 「驗錯了東西」是另一種假陰性

同一個稽核，補完字型之後 `u.ZH` 回報 0 缺字 —— 但畫面上還是一堆方格。
因為**那些字在 `u.ZH` 裡有、在 `F_NUM_S`（Montserrat）裡沒有**，
而頁面拿 `F_NUM_S` 去畫中文。

> **問「這個字有沒有 glyph」之前，要先問「這個 label 用哪一顆字型」。**

### 9.3 `try/except` 會把錯誤變成「安靜的錯值」

```python
try:
    return int(now.peer_cap())      # 板上的 now_bus.py 是舊的，沒這個方法
except Exception:
    return 19                        # ← 安靜地回一個錯的上限
```

板上的檔案比 repo 舊 → `AttributeError` → 落到 except → **回 19**。
「加密時上限應該是 6」會**安靜地顯示 19**，完全不會報錯。

> **動到既有 API 之後，上板前先問板子有沒有那個方法：**
> ```python
> for n in ("peer_cap", "set_encrypt", "clear_peers"):
>     print(n, hasattr(bus.get_service("NowBus"), n))
> ```

### 9.4 板上的檔案可能比 repo 舊，而**沒有東西會告訴你**

同一件事的另一面：不要假設「repo 有 = 板上有」。
`board_sync.py` 的 manifest 讀取在這塊固件上會失敗（會 fallback 成全量），
所以「有沒有同步到」要用**功能探測**確認，不是看時間戳。

## 10. 一頁速查

```
【指令】
  0x1002  SLAVE_ANNOUNCE   節點→廣播   「我開機了」（開機一次）
  0x100D  IDENTIFY_REQ     遙控器→廣播 「你是誰？」（reply_cid 決定回哪裡）
  0x100E  IDENTIFY_RSP     節點→單播   「我是誰」（cid 的唯一來源）
  0x1016  SET_MASTER       遙控器→單播 「以後回給我」（方向，無 ACK）

【流程】公告（學 MAC）→ 掃描（學 cid）→ 綁定（定方向）→ 操作

【原則】
  身分 ≠ 方向           0x1016 是唯一的「方向」寫入者
  掃描不改方向           掃描只問「你是誰」
  廣播回覆要節流         鍵是「問的人的 MAC」，不是 bool
  抖動只在 0x100D        因為只有它會 N 台同時回話
  綁定要 cid             所以掃描是綁定的前置步驟

【顏色】
  綠=目標  琥珀=這次掃到  紅=叫了不應  灰=還沒掃過
```

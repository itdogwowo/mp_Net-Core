先看全局：這套協議在忙什麼

一句話：一個上層（Server / PC / 遙控器）用同一種封包，控制很多台 ESP32，而且不管中間走的是網路線、WiFi、還是 UART 排線。

📦一個封包，五種通道

NC4 只管「封包長什麼樣」。同樣的位元組可以走 WebSocket、UDP、TCP、UART、ESP-NOW。 換通道不用改指令、不用改解析程式——這是整個設計最重要的取捨。

🎯誰在講話，講給誰

封包裡有一個 ADDR（2 B）。裝置只收「廣播」或「寫我位址」的封包， 其餘直接丟掉——所以同一條匯流排上掛十台也不會互相干擾。

🧩指令是什麼，由設定檔決定

「0x1002 這個指令帶著哪些欄位」不是寫死在程式裡，而是寫在 schema/*.json。加指令＝改 JSON ＋ 寫一個處理函式。

🔒每個封包都自帶驗證

尾端 4 B 的 CRC32 涵蓋「檔頭扣掉標記」＋「整個負載」。 位元組錯了就整包丟掉，不會把壞資料當指令執行。

02

分層：同一件事的三種講法

大部分「看不懂」都來自把這三層混在一起講。先把它們分開，後面就都通了。

①通道層

「東西怎麼過去的」

WebSocket / UDP / TCP / UART / ESP-NOW。這一層完全不知道你在傳什麼指令， 只負責搬位元組。它壞掉＝連線問題。

②位元組層

「這串位元組是不是一個完整、沒壞的封包」

SOF / 版本 / 長度 / CRC32。這一層只做一件事：把連續位元組流切成一幀一幀。 它壞掉＝CRC 錯誤、一直等資料。

③指令層

「這幀要做什麼、參數是多少」

CMD 碼 ＋ schema 定義的負載。這一層才開始有意義。 它壞掉＝欄位解錯、動作做錯。

出問題時，「分層」就是你的第一把刀：完全沒反應 → 通道層； 封包收到了但被丟掉 → 位元組層；動作了但不是你要的 → 指令層。 第 9 章有一張對照表可以直接查。

封包解剖：一個真實的 26 位元組

下面是真實跑出來的一幀——一台編號 11401 的裝置開機時廣播「我是誰」。 滑過或點任何一個位元組方塊，下面會告訴你它是什麼。

SLAVE_ANNOUNCE（0x1002）— 從機 → 廣播 — 共 26 B

位元組不是隨機排的，順序有理由

欄位大小在本幀的值為什麼在這裡
SOF2 B4e 43（"NC"） 放最前面，因為解析器要在雜訊裡「找起點」。兩個位元組比一個位元組不容易誤判。
VER1 B04 在 SOF 後面。舊版是 3、用 CRC16；現在是 4、用 CRC32。解析器靠它決定要不要繼續解。
ADDR2 Bff ff（廣播） 放檔頭而不是負載：通道層才能先過濾，不是寫給我的封包連解都不用解。
CMD2 B02 10（= 0x1002） 先有指令碼，才知道負載要用哪套 schema 解。
LEN2 B0d 00（= 13） 放負載前面：解析器先知道「還要等幾個位元組才湊成一幀」，才能處理斷在半路的資料。
DATA變長13 B 真正的內容。長度 0 是合法的（例如「查狀態」這種不帶參數的指令）。
CRC324 B38 cd 53 fb 一定在最後：要等所有內容到齊才算得出來。
⚠ 所有數字都是「小端序」（little-endian）

LEN = 13 在位元組裡是 0d 00，不是 00 0d。 0x1002 是 02 10。寫對接工具時最常死在這裡。

CRC32 的涵蓋範圍刻意不含 SOF

範圍是 buffer[2 : 9+LEN]＝從 VER 到負載結尾。 不含開頭的 "NC"（那只是同步標記），也不含 CRC 自己（算不出來）。

原始碼長這樣

# slave/lib/sys/proto.py — 組包的核心（節錄）
ln = len(payload)
total = HDR_LEN + ln + CRC_LEN          # 9 + 13 + 4 = 26

# 1. 檔頭 9 B：用 struct 一次寫完
struct.pack_into("<2sBHHH", b, off, SOF, CUR_VER, addr, cmd, ln)
#                        ↑    ↑      ↑     ↑    ↑
#                      2B SOF 1B VER 2B ADDR 2B CMD 2B LEN

# 2. 負載：直接寫進緩衝，不另外建 bytes
b[off + HDR_LEN : off + HDR_LEN + ln] = payload

# 3. CRC32：範圍是 header[2:] + payload（不含 SOF、不含 CRC 自己）
crc_val = binascii.crc32(b[off + 2 : off + HDR_LEN + ln], 0) & 0xFFFFFFFF
struct.pack_into("<I", b, off + HDR_LEN + ln, crc_val)
04

黏包拆包：位元組流不是一封一封來的

如果你是從 UDP 來的，可能會以為「一次收 = 一個封包」。但在 TCP、WebSocket、UART 上， 位元組是連續一直流的：三個封包可能擠在一起到，一個封包也可能斷成兩半。 解析器的全部工作就是「把這條水流切回一幀一幀」。

🧷黏包

兩幀黏在一起到。做法：切掉第一幀後不要清空緩衝，繼續在原地找下一個 SOF。

✂️拆包（半包）

幀只到一半。做法：算出 9 + LEN + 4，發現不夠就原地等，下次資料到了接在後面。

🧭錯位

遇到雜訊或壞封包。做法：只往前移 1 個位元組重新找 "NC"，而不是整包丟掉重來。

規則只有五條

①
找 SOF
在緩衝裡找 "NC"。找不到就等更多資料，並丟掉不可能構成開頭的殘留。
②
驗版本／長度
VER ≠ 4 或 LEN > 8192 → 這不是有效開頭，往前移 1 B 繼續找。
③
湊齊一幀
需要 9 + LEN + 4 個位元組。不夠 → 保留緩衝，等下一批。
④
驗 CRC32
通過才交出去。失敗 → 往前移 1 B，把它當成錯位資料。
⑤
交出並前進
負載是零拷貝的記憶體視圖，指向緩衝內部，不另外複製。
第 ② 條的長度檢查不是多餘的

如果解到一段雜訊，剛好湊出 "NC"，後面兩個位元組又剛好被當成 LEN， 就可能得到「這一幀有 60000 個位元組」這種荒謬值。不擋的話，解析器會一直等一個永遠不會來的封包， 甚至把記憶體撐爆。max_len = 8192 就是這個保險。

for ver, addr, cmd, payload in parser.pop():
    # pop() 會多做一次 bytes() 複製，所以可以安全留著
    handle(cmd, payload)

05

負載：指令的「長相」寫在設定檔裡

封包只告訴你「這是 0x1002」和「負載有 13 個位元組」。 至於這 13 個位元組要切成哪幾個欄位、每個欄位幾 bytes，由 slave/schema/sys.json 決定。這叫 schema 驅動。

✅好處

加新指令不用碰解析器、不用改協議。改一個 JSON ＋ 寫一個處理函式就好。 對接方也可以直接讀 JSON 當文件。

⚠️代價

「欄位順序」就是合約。順序改了、型別改了，就是無聲的破壞性變更—— 而且是兩邊都不會報錯的那種。

支援的型別只有六種

全部都是小端序。知道這六種，你就能看懂任何一條指令的負載。

型別type code佔幾個位元組怎麼排
u801無號整數 0–255
u1612無號整數 0–65535，小端序
u3224無號整數，小端序
str_u16len32 ＋ 內容長度 先 2 B 長度，再 UTF-8 內容。長度是位元組數，不是字數——中文一個字 3 B。
bytes_fixed4固定在 JSON 的 len 例如 sha256 就是 32 B，不足補 0、超過截掉。
bytes_rest5吃掉剩下的全部 必須放最後一個欄位。適合「檔案片段」這種長度不定的資料。
關於 encode 與 decode 的小陷阱

SchemaCodec.encode 其實還支援 i16 / i32（有號整數）， 但 schema_loader 沒有給它們 type code（會落成 255），所以解不回來。 目前所有 schema JSON 都只用上面六種——別在 JSON 裡寫 i16。

定址：這台裝置有兩個名字

這是整份文件裡最容易誤解的一段。原因很簡單：同一個裝置在兩層各有一個位址， 而且它們不能互推。先把兩層分開看。

協議層 · 2 bytes · 寫在封包的 ADDR 欄位
我的名字（協定位址）cid = 0x0002
程式裡叫 bus.cid
我上級的名字master_cid
未設定 = 0xFFFF
廣播0xFFFF
大家都要收
▲不可互推：一個是「誰」，一個是「怎麼送到」▼
射頻層 · 6 bytes · 送出去時才決定
我的實際位址MAC
程式裡叫 slave_id（歷史名，其實就是 MAC）
我上級的實際位址master_mac
主動發送時才需要
這一幀從哪來src_mac
射頻層免費附帶，不用對方講

三個最常見的誤解

✗「cid 就是 MAC 的簡寫」

不是。cid 是 2 B 的協議位址，可以手寫（面板就是 "0001"）； MAC 是 6 B 的射頻位址，晶片出廠就有。兩者不可互推。

✗「src_mac 就是 master_mac」

只有剛好上級在講話時才相同。前者是「這一幀誰講的」，後者是「我上級是誰」。 延後發射（抖動）時必須用前者，因為那時講話的人早就換了。

✗「slave_id 是另一個編號」

它就是 MAC。只是歷史名字沿用下來，出現在心跳、 0x100E、peers 表 key 等很多地方。看到它就想成「這台的 MAC」。

完整流程：遙控器怎麼找到一台節點

四步，四個指令。注意每一步「協議層填什麼」和「射頻層送去哪」是分開決定的。

步驟指令協議層 ADDR射頻層去向誰決定的
① 點名0x100D0xFFFF 廣播廣播 MAC 發起方直接指定
② 回應0x100E負載裡的 reply_cidsrc_mac 兩個不同來源：一個來自負載，一個來自射頻層
③ 記住———遙控器端自己存
④ 定方向0x10160x0002 單播master_mac 唯一寫入者；寫入後會落盤
為什麼「回覆」的位址不直接用 MAC？（第一個理由是決定性的）

1. UART / RS485 根本沒有 MAC。共用匯流排上沒有「射頻來源」可以學， 而廣播掃描的幀頭是 0xFFFF—— 這時 reply_cid 是唯一能知道「該回給誰」的途徑。 整條流程的前提是「傳輸層無關」，改成 MAC 在共用匯流排上就做不出來。

2. 負載裡的 MAC 可以說謊。射頻來源是發送者的實際位址（學不到假的）， payload 只是對方填的字串。用 payload 的 MAC 當目的地＝任何人都能叫你去打第三台。

3. 兩個位址本來就活在兩層。硬塞成一個，會讓「哪一層」的資訊消失。

那什麼時候真的需要「存下來的 MAC」？

主動發送時（開機公告 0x1002、心跳）。 那條路沒有幀進來，所以沒有 src_mac 可以學—— 只能靠 master_mac。它的存在就是為了這個， 而它的值取自 0x1016 收幀當下的 src_mac（跟 0x100E 帶回 cid 的方式完全對稱）。

封包怎麼被過濾（app.handle_stream）

# 只收兩種封包，其餘直接丟掉
if addr != ADDR_BROADCAST and addr != bus.cid:
    continue      # 不是廣播、也不是寫給我 → 不干我的事

這條規則是「同一條匯流排掛很多台」的基礎。也因為它， 「逐位址掃描」在接收端是現成可用的。

傳輸：同一包，五條路

這一章要回答一個常見疑問：「既然封包一樣，那換通道到底差在哪？」 答案是：差在「誰負責切幀」和「有沒有額外的前綴」。

CTRL-WS
lib/sys/net_bus.py (TYPE_WS)
WebSocket。主控制通道，指令、回覆、串流都走這裡。
訊息邊界天然存在
UDP-DISCV
lib/sys/net_bus.py (TYPE_UDP)
UDP 廣播發現，預設埠 9000。用來「找到對方在哪」。
一個 datagram = 一幀
TCP
lib/sys/net_bus.py (TYPE_TCP)
備用／直連。純位元組流，最需要 StreamParser。
會黏包、會拆包
CIRCUIT
lib/sys/circuit_bus.py
UART 實體線。有線控制，也是 bus_speed 臨時提速的對象。
慢，但最穩
NOW-Bus
lib/sys/now_bus.py
ESP-NOW。沒有 WiFi 也能用的短距離控制。
射頻層帶 src_mac

環形緩衝的槽位佈局：有一個 2 B 前綴

位元組收進來之後，寫進各 bus 的 AtomicStreamHub 時會加一個長度前綴。 這個前綴不是 NC4 的一部分——它是內部傳遞用的，BusDecodeTask 讀出來時會剝掉。

u16 LE：這幀有多長 ＋ 完整的 NC4 封包（從 "NC" 開始）

[0:2] = 長度 n　[2:2+n] = NC4 封包。 也就是說：StreamParser 看到的永遠是乾淨的 NC4 封包，前綴在更早的地方就沒了。

「為什麼我的 26 個位元組還沒到？」

同樣一幀，不同通道的耗時差很多。這張表可以幫你判斷「慢」是正常的還是壞了。

通道一幀 26 B 的實際耗時換算什麼時候會覺得慢
WiFi（WS/TCP/UDP）約 1 ms 等級 + 排程抖動—大量小封包時，是排程而不是頻寬在限制
UART 11520026 × 10 ÷ 115200 ≈ 2.3 ms≈ 11.5 KB/s傳檔時非常明顯
UART 921600≈ 0.28 ms≈ 92 KB/s這就是 bus_speed 要解決的事
ESP-NOW約 1–3 ms／幀—有每幀開銷，不適合高速串流

計算是「每 byte 10 bits」（8 資料 ＋ 1 起始 ＋ 1 停止）。所以 115200 baud ≈ 11520 B/s。 完整協商流程、時序與失敗處理見 doc/01_protocol/09_bus_speed_protocol.md。

這裡就是「分層」發揮作用的地方

整份 NC4 只有一個地方知道「怎麼送」：bus。也只有一個地方知道「怎麼切幀」：StreamParser。 所以換通道＝換一個 bus 實作，協議本身、指令、schema、處理函式一個字都不用改。

112 條指令長什麼樣

09

壞掉的時候怎麼查

照「分層」的順序往下問，一次砍掉一半的可能。先看症狀，再對照原因。

症狀最可能在哪一層常見原因怎麼確認
對方完全沒反應，連 log 都沒有 ① 通道層 位址或埠不對、線沒接、WiFi 沒起來、ESP-NOW 沒配對 先在通道層確認「位元組有沒有進來」
位元組進來了，但一直沒有反應 ② 位元組層 解析器一直「等待中」：LEN 被解成很大、或 SOF 之後就斷了 看緩衝區是不是只增不減；看 LEN 欄位解出來的值
封包被丟掉，CRC 一直失敗 ② 位元組層 ① 對端 CRC 算法／範圍不同 ② 版本不是 4（舊版用 CRC16）③ 位元組在傳輸中真的壞了 自己算一次 crc32(buf[2:9+LEN]) 跟封包尾端比
CRC 對，但欄位值是垃圾 ③ 指令層 schema 欄位順序／型別跟對端不一致；或中間插了新的欄位 拿 schema JSON 逐欄位對位元組
數值差很多（例如 300 變成 7680） ③ 指令層 端序搞錯：0d 00 被當成 big-endian 讀成 0x0d00 確認是 <H（little-endian）不是 >H
字串尾巴多出亂碼 ③ 指令層 str_u16len 的長度是「位元組數」不是「字數」，中文一個字 3 B 比對 len(s.encode('utf-8'))
指令有執行，但回覆收不到 ④ 定址 還沒 0x1016 SET_MASTER：master_cid 還是 0xFFFF， 回覆變成廣播（或沒人認領） 先做一次配對；確認 bus.master_cid
換了通道就壞掉 ① 通道層 把「射頻層學到的東西」寫進了指令層：例如假設一定有 src_mac （UART 上沒有） 問自己：這一行的資訊在共用匯流排上還存在嗎？
最難查的一類：安靜的錯值

欄位順序或型別錯了，通常不會報錯——它會解出一個「看起來合理」的值， 然後動作做錯。所以：對接新指令時，先驗證再相信。 拿一條已知答案的指令（例如 0x1004 帶 01 01）走一遍全鏈路， 確認欄位解出來跟預期一樣，再去測新指令。

模擬器

一台 Master（面板 0x0001）接在匯流排上，掛著兩台 Slave （0x0002 燈條 A、0x0003 燈條 B）—— 三台的 cid 互不相同。 先在下面選發送目標，再按左邊控制盤的指令；右邊拓撲會畫出封包怎麼走、 哪台收到、誰回話、誰撞線（也可以點板子斷電、點線拔線）。 規則照 doc/01_protocol/ 的協議定義，欄位與 slave/schema/*.json 一致。

三台的位址怎麼分

Master／面板 = 0x0001：它自己的 cid，不是任何節點的。 節點是 0x0002、0x0003。 所以「已配對」時回覆的 ADDR=0x0001 不會被任何節點誤收 —— 這也是為什麼 0x1016 SET_MASTER 帶的是發起方自己的 cid。

每一台節點各自記自己的 master_cid（未設 = 0xFFFF）： 0x1016 只改「收到那一幀的那一台」，其餘節點不受影響 —— 在「⑤ 線路狀態」可以一台一台切換看差別。

這個模擬器要你看見的事

① 控制類指令永遠不會有回覆。0x3105/0x3106 送出去， 只能靠「燈變了」和板子的 log 確認 —— 模擬器裡就是看上面的燈。

② 回覆的位址 = 那一台自己的 master_cid。 未配對是 0xFFFF，連查詢的回覆都會變成廣播幀 （只有 0x100E 例外，它用請求裡的 reply_cid）。 配對與否每台各自獨立（見「⑤ 線路狀態」）。

③ 廣播查詢（0x3101/0x3107）沒有抖動機制 → 必撞。 兩台都通過位址過濾、都回話，線上就是兩份位元組疊在一起。 這不是 bug，是「廣播查詢」本來就不該用。

④ 抖動（0x100D 的 timeout_ms）只降低碰撞機率，不保證不撞。 每台各自抽 [0, timeout_ms] 的隨機延遲；抽到相同（或差不到一個幀的傳輸時間）時槽 還是會撞 —— 多按幾次「點名」就會遇到。視窗開大一點可以再降機率。

模擬結果依 doc/01_protocol/ 的協議定義：位址過濾、回覆位址（master_cid／ reply_cid）、無 ACK 的指令、廣播查詢撞線、抖動視窗。欄位與 slave/schema/*.json 一致。想把原理讀過一遍，切到「圖文導讀」分頁。

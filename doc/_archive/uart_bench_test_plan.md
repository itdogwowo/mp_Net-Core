## 0. 先講三條「協議沒寫、但實作遵守」的規則

這三條是這次測試**最容易踩的坑**，先看再動手：

### 規則 1 — 燈效控制是**單向**的，不會回 ACK

| 指令 | 誰發 | 有回覆嗎 |
|---|---|---|
| `0x3105 MODE_SET`（播放） | Master | ❌ **不回** |
| `0x3106 MODE_STOP`（停止） | Master | ❌ **不回** |
| `0x3107 MODE_DETAIL_QUERY` | Master | ✅ 回 `0x3108` |
| `0x3101 MODE_LIST_QUERY` | Master | ✅ 回 `0x3102` |
| `0x3103 / 0x3104 MODE_GET` | — | 🚫 schema 有定義但**未實作**，永遠不會有回覆 |

> **判準**：schema JSON 裏**沒有**任何「回不回」的欄位。要不要回覆完全由
> `slave/action/*.py` 的 handler 決定 —— 所以**看 schema 看不出來**，必須看程式碼。
> `_send(ctx, rsp_cmd, ...)` 有被呼叫才會回。

**「指令有送出去」的證據只有兩個**：板上序列埠的 `print`，以及**燈真的變了**。

### 規則 2 — 廣播 `0xFFFF` 出去，**不應該**收到回覆

理由不是「禮貌」，是因為**共用媒介上會撞線**：

- 射頻（ESP-NOW）有 `src_mac` 可以學「剛剛誰講話」，所以能定向回覆。
- **共用線（UART/RS485）沒有** —— 廣播時幀頭是 `0xFFFF`，Slave 沒有任何資訊知道該回給誰。
- 若 N 台同時回，線路上就是**硬碰撞**，全部爛掉。

這也是為什麼 `0x100D IDENTIFY_REQ` 要帶一個 `reply_cid` 欄位，而且回覆要**隨機延遲**（抖動）。

### 規則 3 — RS485 半雙工有 listen-before-talk（LBT），會影響你的時序

`slave/driver/uart_drv.py` 的 `_Rs485Uart.write()` 在發送前會**先聽線路**，
連續 `max(2, 3×byte_time)` 毫秒安靜才拉高 DE（方向腳），拉高後再等
`en_settle_ms`（預設 **1ms**）才真正送出。

兩個實務後果：

1. **Master 送完不能馬上期待回覆** —— Slave 要先等線路安靜 + 1ms DE 建立。
   建議 Master 送完後**至少等 50~100ms** 再讀回覆。
2. ⚠️ **`_wait_bus_quiet()` 會把聽到的資料讀掉丟棄**（註解明寫「不是給我的」）。
   所以如果 Master 在 Slave 回覆期間又發下一包，**那個回覆會消失**。

> 📌 未解問題（見 §9）：`0x3102`/`0x3108` 的回覆**沒有抖動**、
> 而且目前的回覆幀 `ADDR` 固定是 `0xFFFF`。這兩件事在兩台機同時回時會出事。

## 1. 測試環境

```
        USB-UART 轉接頭（PC 當 Master）
                 │
        ┌────────┴────────┐          ← 三條線併接：TX / RX / GND
        │                 │
   ┌────┴────┐       ┌────┴────┐
   │ S3 #1   │       │ S3 #2   │
   │ cID0001 │       │ cID0002 │
   └─────────┘       └─────────┘
```

### 1.1 硬體接法（純 TTL，最省事）

| PC 轉接頭 | 接去哪 |
|---|---|
| TX | **兩台**的 RX（GPIO 由 config 決定） |
| RX | **兩台**的 TX |
| GND | **兩台**的 GND（一定要共地） |

> ⚠️ **兩台同時驅動 TX 會有電氣衝突**（一個推高、一個拉低 = 短路電流）。
> 測試 §7（單播回覆）沒問題，因為同時間只有一台在講。
> 但 **§8（廣播）會讓兩台同時回** —— 這正是要測的現象，短時間沒關係，別長時間掛著。
> 正式環境請用 RS485 收發器（MAX485 之類）＋ `GPIO.en` 方向腳。

### 1.2 板端設定：`slave/config.json`

**每個測試例之前必做**（`UART.enable` 預設是 **0**，不開什麼都不會發生）：

```json
{
  "UART": {
    "enable": 1,
    "list": [
      {
        "id": 1,
        "baudrate": 115200,
        "GPIO": { "tx": 17, "rx": 18 }
      }
    ]
  }
}
```

- `id` = `machine.UART(id)` 的硬體周邊號（**1 起**）。
- `tx` / `rx` = **接腳編號**，照你的接線填。
- 用 RS485 收發器時再加 `"en": <DE/RE 腳>`，並可選 `"en_settle_ms": 1`。
- `CircuitDecode.enable`（預設 0）是**再上一層的篩選**，不填也通；填了才只啟用指定線。

### 1.3 兩台機的位址：`System.cID`

`cID` 是**協議層位址**（2 B），不是 MAC。預設 `""`，開機時
`ConfigManager.ensure_cID()` 會自動用 `machine.unique_id()` 末 4 碼填入
（例如 MAC 尾碼 `A1B2` → cID `0xA1B2`），並**自動落盤**。

**為了可重現，直接寫死**：

| 板子 | `slave/config.json` 的 `System` 段 |
|---|---|
| S3 #1 | `"cID": "0001"` |
| S3 #2 | `"cID": "0002"` |

> 開機 log 會印 `[Config] ✓ cID auto-filled: XXXX`（只在自動填的時候）。
> 寫死的話不會印，但 `0x100E` 查得出來。

⚠️ **不要**用 `0x1103 STATUS_SET` 線上改 `cID` 期待立即生效 ——
`bus.cid` 只在 ConfigManager 推動時更新，線上改快取**不會**同步過去（要重開機）。
本手冊一律走「改 config + 重開機」。

### 1.4 燈效模式 ID

`(mode_type, mode_id)` **兩個欄位合起來**才是模式的唯一識別碼：

| `mode_type` | 意義 | `mode_id` 語義 |
|---|---|---|
| `1` | **LED 組** | LED 模式表內索引 |
| `2` | SERVO 組 | SERVO 模式表內索引 |
| `3` | AUDIO 組（純音效） | 音效模式索引 |
| `0` | 系統模式 | 只出現在回報，**不能用 MODE_SET 指定** |

本手冊範例用 `(1, 1)` = LED 組的第 1 個模式。
**你板上的實際 ID 必須先撈**（測試 T4 會做這件事），不要照抄。

## 2. 回覆對照總表（貼在牆上那張）

| 送出的指令 | `addr=0xFFFF`（廣播） | `addr=0x0001`（指定） |
|---|---|---|
| `0x3105 MODE_SET` | 兩台都播 ｜ **無回覆** | 只有 #1 播 ｜ **無回覆** |
| `0x3106 MODE_STOP` | 兩台都停 ｜ **無回覆** | 只有 #1 停 ｜ **無回覆** |
| `0x3107 MODE_DETAIL_QUERY` | ⚠️ **兩台都回 → 撞線** | ✅ **只有 #1 回 `0x3108`** |
| `0x3101 MODE_LIST_QUERY` | ⚠️ **兩台都回 → 撞線** | ✅ **只有 #1 回 `0x3102`** |
| 任意指令送到 `0x0003` | — | **完全沒反應**（沒有人認領） |
| CRC 錯的任意指令 | **完全沒反應**（解析器丟掉） | **完全沒反應** |

**一句話總結**：要回覆就用**指定位址**；要動作（燈效）才用廣播。

## 4. 測試例（逐一）

### T1 — 廣播點名：找機（`0x100D`）

**送這個**（`0x100D IDENTIFY_REQ`，`reply_cid=0x0001`＝PC 自己的位址，`timeout_ms=50`＝抖動視窗）：

```
4e 43 04 ff ff 0d 10 05 00 01 00 32 00 00 3b 58 ec 46
│        │     │     │  └ payload（5 B）: reply_cid=0001, timeout_ms=0032, force=00
│        │     │     └ LEN = 5
│        │     └ CMD = 0x100D
│        └ ADDR = 0xFFFF（廣播）
└ SOF "NC"（2 B）
```

> ⚠️ **`0x100D` 有三個欄位**（`reply_cid` + `timeout_ms` + `force`）。
> 只寫前兩個 → 長度會是 4 不是 5 → CRC 全錯 → 板子整幀丟掉。
> 這是最容易手寫錯的一條。

**期待的反應**

| 觀察點 | 預期 |
|---|---|
| 兩台序列埠 | 各印一行（抖動 0~50ms 後才回） |
| PC 收到 | **兩個** `0x100E` 幀，`ADDR=0x0001`（= 你送的 `reply_cid`） |
| 回覆內容 | #1 的 payload 帶 `cid=0001`、#2 帶 `cid=0002` |

回覆格式（`0x100E IDENTIFY_RSP`）：

```
4e 43 04 01 00 0e 10 ...   ← ADDR 是你指定的 reply_cid
```

> **這一步是唯一該用廣播又要回覆的例外** —— 因為它帶了 `reply_cid`，
> 而且有**抖動**把兩台的發射時間錯開。對照 T10 就知道差別在哪。

---

### T2 — 指定點名（只點 #1）

把 `ADDR` 改成 `01 00`，並重算 CRC：

```
4e 43 04 01 00 0d 10 05 00 01 00 32 00 00 45 c3 1e 7c
```

**期待**：#1 回 `0x100E`，**#2 完全安靜**。

> 這是驗證**位址過濾**最乾淨的一步。#2 明明在線上也收到了同一批位元組，
> 但 `app.handle_stream` 會判斷 `addr != 0xFFFF && addr != my_cid` → 直接丟掉。

---

### T3 — 點名不存在的位址（`0x0003`）

```
4e 43 04 03 00 0d 10 05 00 01 00 32 00 00 84 7a 72 24
```

**期待**：**兩台都不回**，PC 等 100ms 後什麼都沒收到。

> 用來確認「沒有反應」不等於「線壞了」—— 前一步才剛成功過。

---

### T4 — 查模式清單（`0x3101`）→ 撈出真正的 mode_id

**送這個**（指定 #1，`mode_type=1` = LED 組）：

```
4e 43 04 01 00 01 31 01 00 01 f2 36 2d 44
```

**期待的回覆**（`0x3102 MODE_LIST_RSP`）：

```
4e 43 04 ff ff 02 31 04 00 01 01 01 01 39 fe 94 73
│           │     │     │  │  │  └ entries: 每筆 2 B，u16 LE
│           │     │     │  │  └ count = 1
│           │     │     │  └ mode_type = 1（回音）
│           │     └ LEN = 4
│           └ ADDR = 0xFFFF ← ⚠️ 目前實作固定廣播，見 §9
└ SOF
```

**怎麼讀 `entries`**：每筆 2 B、**小端序**，內容是**內部 16-bit 模式 id**
= `(mode_type << 8) | mode_id`。

例：`01 01` → `0x0101` → 拆回 `mode_type = 0x01`、`mode_id = 0x01`。

> ⚠️ **`0x3101` 和 `0x3107` 的 `mode_type` 語義不同**：
> 前者是「組別選擇」（0=全部／1=LED／2=SERVO／3=AUDIO），
> 後者是「模式識別碼高位」。兩者都叫 `mode_type`，但用法不同。

**拿到真實 id 後，T5~T9 的 `mode_id` 請換成你撈到的值**（下面是 `mode_id=1` 的範例）。

---

### T5 — 查模式細節（`0x3107`）→ 拿到模式名稱

**送這個**（指定 #1）：

```
4e 43 04 01 00 07 31 02 00 01 01 ee 2d 1e 32
```

**期待的回覆**（`0x3108 MODE_DETAIL_RSP`，以名稱 `demo_eyes` 為例）：

```
4e 43 04 ff ff 08 31 11 00 01 01 00 00 00 00 09 00 64 65 6d 6f 5f 65 79 65 73 ef c7 89 53
                │     │  │  │           │  │  └ "demo_eyes"（UTF-8，9 個位元組）
                │     │  │  │           │  └ name 長度 = 9（u16 LE）
                │     │  │  │           └ total_ms = 0（目前無資料，恆為 0）
                │     │  │  └ mode_id = 1
                │     │  └ mode_type = 1
                │     └ LEN = 17
                └ CMD = 0x3108
```

- 名稱長度是**位元組數**，不是字數（中文一個字 3 B）。
- 模式不存在時 `name` 會是**空字串**（長度 `00 00`），**不會報錯** ——
  所以「回覆長度很短」是「模式 ID 打錯」的訊號。
- 板上**不會印任何 log**（這個 handler 沒有 print），只有回覆。

---

### T6 — 單播播放燈效（`0x3105` → #1）

**送這個**：

```
4e 43 04 01 00 05 31 05 00 01 01 00 00 ff 83 ba 4b 40
                │     │     │  │  │  │  └ brightness = 255（= 不改亮度）
                │     │     │  │  │  └ start_delay_ms = 0
                │     │     │  │  └ mode_id = 1
                │     │     │  └ mode_type = 1（LED 組）
                │     │     └ LEN = 5
                │     └ CMD = 0x3105
                └ ADDR = 0x0001（只給 #1）
```

**期待的反應**

| 觀察點 | 預期 |
|---|---|
| **#1 的燈** | ✅ **開始播指定的燈效** |
| **#2 的燈** | ❌ **完全不動**（位址被過濾掉） |
| #1 序列埠 | 印 `[Pixel] MODE_SET type=1 id=1 bri=255 delay=0ms` |
| #2 序列埠 | **什麼都不印** |
| **PC 收到** | **什麼都沒有** ← ⚠️ 這條指令不回 ACK |

> **`brightness` 的坑**：`255` = **不改**（沿用目前值），`0` = **最暗/關**（合法值）。
> 所以「我叫它播但燈是暗的」通常是你送了 `0` 而不是 `255`。
> 想設亮度就送 `0~254`。

---

### T7 — 單播播放到 #2

把 `ADDR` 改成 `02 00`，CRC 會跟著變：

```
4e 43 04 02 00 05 31 05 00 01 01 00 00 ff 82 dc a9 d9
```

**期待**：只有 **#2** 變燈；#2 印 `[Pixel] MODE_SET ...`；#1 安靜；**PC 沒有回覆**。

> T6 + T7 合起來就是你要的「四個指令控制兩台機」的前兩個。
> 這裡請**刻意讓兩台跑不同模式**（例如 #1 用 `mode_id=1`、#2 用 `mode_id=2`），
> 這樣一眼就能看出「指令真的只打到指定那台」。

---

### T8 — 廣播播放：兩台同步（`0xFFFF`）

```
4e 43 04 ff ff 05 31 05 00 01 01 00 00 ff fd 21 b9 7a
```

**期待的反應**

| 觀察點 | 預期 |
|---|---|
| **兩台的燈** | ✅ **同時**開始播（同一個 `start_delay_ms`） |
| 兩台序列埠 | **各印一行** `[Pixel] MODE_SET type=1 id=1 bri=255 delay=0ms` |
| **PC 收到** | **什麼都沒有** |

> **這才是「同步」的正確用法**：兩台收到**同一個** `start_delay_ms`，
> 各自延遲相同時間後起播，看起來就是一齊動。
> 想要精準同步（誤差 < 10ms），可以先用 `0x100A TIME_SYNC` 對時。

---

### T9 — 廣播停止（`0x3106`）

```
4e 43 04 ff ff 06 31 01 00 01 aa 00 88 26
```

`action`：**0 = 暫停**、**1 = 全關閉**（上面是 1）。

**期待**：兩台的燈**同時熄**；兩台各印 `[Pixel] MODE_STOP action=1`；**PC 沒有回覆**。

---

### T10 — 廣播查詢：預期會撞線（⚠️ 負面示範）

```
4e 43 04 ff ff 07 31 02 00 01 01 a6 61 c9 4a
```

**這個測試的目的是「看到它壞掉」，藉此證明規則 2。**

**預期的三種結果**（都不算「測試失敗」）：

1. **PC 什麼都沒收到** —— 最可能。兩台同時驅動 TX，位元組互相蓋掉，CRC 全掛。
2. **只收到一台的回覆** —— 另一台撞輸了。
3. **收到一幀但 CRC 錯** —— 你的 PC 端 parser 應該把它丟掉（**這正是驗證你的 parser 的好機會**）。

**為什麼會這樣（機制）**：

- 兩台都通過了位址過濾（廣播嘛），都執行 handler，都呼叫 `_send()`。
- 回覆幀的 `ADDR` 是 `0xFFFF`（見 §9），所以**沒有任何一台會因為位址而不回**。
- 兩台的 LBT 幾乎同時看到線路安靜 → 幾乎同時拉 DE → 同時發射 → **碰撞**。
- 對照 T1：`0x100D` 有 `timeout_ms=50` 的**隨機延遲**，所以兩台錯開了。

> 📌 **這不是 bug，是「廣播查詢」本來就不該用**。正確做法是 T4/T5 的**指定查詢**。

---

### T11 — CRC 壞掉：解析器必須丟掉

拿 T6 的封包，把最後 1 個位元組改掉：

```
4e 43 04 01 00 05 31 05 00 01 01 00 00 ff 83 ba 4b 41
                                                  ↑ 原本是 40
```

**期待**：**完全沒反應**。燈不動、沒有 log、沒有回覆。

> **這裡要驗證的是你的 PC 端**，不是板子：板子的 `StreamParser` 驗 CRC32 失敗後
> 會**往前移 1 個位元組**重新找 `"NC"`。所以如果你接著送一包**正確**的，
> 它應該還是能正常解出來 —— **這就是「重同步」**。值得單獨測一次。

---

### T12 — 位址不匹配

```
4e 43 04 ff 00 05 31 05 00 01 01 00 00 ff e9 f6 fe 9b     ← ADDR = 0x00FF，沒有這台
```

**期待**：**兩台都不動**。用來確認「燈沒動」不是因為線斷了。

## 5. 送這些位元組的三種方法

### 方法 A — PC 端寫個小工具（建議）

需要 `pyserial`（`pip install pyserial`）：

```python
# 用法: python -B nc4_send.py /dev/cu.usbserial-XXXX "4e 43 04 01 00 07 31 02 00 01 01 ee 2d 1e 32"
import sys, time, serial

port, hexstr = sys.argv[1], sys.argv[2]
data = bytes.fromhex(hexstr.replace(" ", ""))

with serial.Serial(port, 115200, timeout=0.05) as s:
    s.reset_input_buffer()
    s.write(data)
    s.flush()
    t0 = time.time()
    rx = bytearray()
    while time.time() - t0 < 1.0:          # 收 1 秒
        chunk = s.read(256)
        if chunk:
            rx += chunk
            t0 = time.time()               # 有資料就延長
    print("送出:", data.hex(" "))
    print("收到:", rx.hex(" ") if rx else "（無回覆）")
```

> **不需要**自己拆幀才能看到結果 —— 先看 hex 對不對就好。
> 要驗 CRC 的話，把收到的位元組丟給你自己的 parser 測。

### 方法 B — 板端 REPL 自己造（不經 PC）

在任一台板的 REPL 上：

```python
import sys; sys.path.insert(0, "/lib")   # 路徑依你的部署而定
from lib.sys.proto import Proto
from lib.sys.schema_codec import SchemaCodec
from lib.sys.schema_loader import SchemaStore

store = SchemaStore("/schema")
pkt = Proto.pack(0x3107,
                 SchemaCodec.encode(store.get(0x3107), {"mode_type": 1, "mode_id": 1}),
                 addr=0x0001)
print(bytes(pkt).hex(" "))     # 直接看位元組；要送就丟進 bus
```

> 注意 `Proto.pack()` 回傳的是**指向共享 buffer 的 memoryview** ——
> 下一次 `pack()` 會蓋掉它。要留著就 `bytes(pkt)` 複製一份。

### 方法 C — 離線驗證（完全不接線）

不用上板就能確認「你的封包對不對」：

```python
import sys; sys.path.insert(0, "slave")
from lib.sys.proto import Proto
from lib.sys.schema_codec import SchemaCodec
from lib.sys.schema_loader import SchemaStore

store = SchemaStore("slave/schema")
cmd_def = store.get(0x3105)
payload = SchemaCodec.encode(cmd_def, {
    "mode_type": 1, "mode_id": 1, "start_delay_ms": 0, "brightness": 255})
pkt = bytes(Proto.pack(0x3105, payload, addr=0x0001))
print(pkt.hex(" "))
# → 4e 43 04 01 00 05 31 05 00 01 01 00 00 ff 83 ba 4b 40
```

再走一次解碼確認 round-trip：

```python
print(SchemaCodec.decode(cmd_def, payload, store))
# → {'mode_type': 1, 'mode_id': 1, 'start_delay_ms': 0, 'brightness': 255, '_name': ..., '_cmd': ...}
```

## 6. 症狀 → 原因 對照表

| 症狀 | 最可能的原因 | 先查什麼 |
|---|---|---|
| 完全沒反應，板子也沒 log | `UART.enable = 0` | `config.json` 的 `UART` 段 |
| 完全沒反應，板子有開機 log | 接線 TX/RX 反了、沒共地 | 換線試、量 GND |
| 板子有 log 但燈不動 | `brightness` 送了 `0`（最暗） | 改送 `255` 或 `200` |
| 板子有 log 但燈不動 | `mode_id` 不存在 | 先做 T4 撈清單 |
| 兩台都動，但你只想動一台 | `ADDR` 用了 `0xFFFF` | 改成 `01 00` / `02 00` |
| 指定 `0x0001` 但兩台都不動 | 那台的 `cID` 不是 `0x0001` | 做 T1 看它實際回報的 cid |
| 送 `0x3105` 等不到 ACK | **正常**，這條不回覆 | 看燈、看板上 log |
| 送 `0x3107` 指定卻收到兩份 | `ADDR` 其實是廣播 | 檢查位元組第 3~4 位 |
| 收到回覆但 CRC 錯 | 兩台同時回（撞線） | 改用指定查詢（T4/T5） |
| 送完馬上讀，讀不到回覆 | LBT + 1ms DE settle | 送完**等 50~100ms** 再讀 |
| 第二包送出後，第一包的回覆才來但不見了 | `_wait_bus_quiet()` 把資料讀掉丟棄 | 一問一答，不要連續送 |

## 7. 一句話驗收標準

> **指定的查詢有回、廣播的動作兩台都做、兩者都不該有 ACK。**

如果這三句都成立，你的單線鏈路就是通的。

## 9. ⚠️ 已知缺口（測試中會遇到，但**不是你的操作問題**）

這兩點查 code 確認過，屬於**協議層沒寫、實作有洞**的地方：

### 缺口 1 — 燈效回覆的 `ADDR` 固定是 `0xFFFF`

`slave/action/pixel_actions.py` 的 `_send()`：

```python
def _send(ctx, rsp_cmd, fields):
    ...
    ctx["send"](Proto.pack(rsp_cmd, payload))     # ← 沒給 addr
```

而 `Proto.pack(cmd, payload=b"", addr=ADDR_BROADCAST)` —— **預設就是 `0xFFFF`**。

所以 `0x3102` / `0x3108` 的回覆在線路上是**廣播幀**。
根本原因是 **schema 裏沒有「回覆位址」欄位**，handler 無從得知該回給誰
（唯一帶回覆位址的是 `0x100D` 的 `reply_cid`）。

**影響**：兩台同時被查 → 兩台都回 → 撞線（就是 T10 的現象）。
**建議的規則寫法**：

> 共用媒介（UART/RS485）上的回覆，`ADDR` 必須是「**這一幀的來源 cid**」或請求方
> 指定的 `reply_cid`，**永遠不得用 `0xFFFF`**。判準不是「有沒有 `master_cid`」，
> 而是「這條管子有沒有實體位址可回」：射頻層有 `src_mac` 可學，共用線沒有 ——
> 所以共用線只能靠 `reply_cid`。

### 缺口 2 — 燈效回覆沒有抖動（jitter）

`0x100D` 有 `timeout_ms` 抖動視窗把多台的回覆錯開；`0x3101`/`0x3107` **沒有**。

**影響**：即使修好 `ADDR`，廣播查詢在多台場景仍會撞。
**建議**：廣播查詢直接定義為「不保證有回覆」，只支援指定查詢；
或比照 `0x100D` 加一個抖動欄位。

### 缺口 3 — `0x3103` / `0x3104 MODE_GET` 未實作

schema 有定義、**沒有 handler、也沒有任何任務會發出**。
它的用途是取代對方舊系統的 `STATUS_QUERY / STATUS_REPORT`（查「現在在播什麼、播到哪」）。
**目前想查執行狀態是查不到的** —— 這是對接前的待補項。

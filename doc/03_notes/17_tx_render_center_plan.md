# 統一渲染輸出中心（TxCenter）— 問題與目標

> **用途**：架構意圖記錄——為什麼要把「所有匯流排的對外發射」集中到單一渲染／輸出模組。
> **本檔只定「遇到的問題、想解決的問題、目標」**；設計與做法留待日後再想。
> **分類**：筆記（03_notes）
> **狀態**：PLANNED（問題與目標已定，做法未設計）
> **最後更新**：2026-09-19

---

## 1. 一句話

現在全系統有 **11 個地方**各自直接對硬體發射，分散在多個 task、跨 2 個核心，彼此沒有任何仲裁。
我們想要的是：**把所有對外發射集中到單一渲染／輸出模組，由它統一控制所有外圍硬體。**

---

## 2. 我們遇到的問題

### 2.1 結構性問題（現況調查，皆有程式碼依據）

| # | 問題 | 依據 |
|---|---|---|
| P1 | **同一條 UART 多個 writer**：NC4 回覆、馬達幀（`FF addr v FE`）、顯示幀（`B4..FF`）、MP3 指令各自直接呼叫 `uart.write`，沒有鎖也沒有佇列 | `lib/sys/circuit_bus.py:126-158`、`lib/hw/uart_motor.py:338-360`、`tasks/action_task_1.py:388-402`、`lib/hw/mp3_tf_16p.py:69` |
| P2 | **跨核無保護**：`bus_decode`（NC4）在 core0、`render`（像素／馬達的 writer）註冊在 core1，兩個核心理論上可同時寫同一個 `uart` | `Core_Manager.py:81`、`Core_Manager.py:100`（tuple 語意見 `lib/sys/task_manager.py:114, 186`） |
| P3 | **沒有優先級**：不可丟的 NC4 回覆（協議是 stop-and-wait）與可丟的 50fps 像素幀在同一條線上等價排隊，先到先寫 | `tasks/bus_decode.py:74-80`、`tasks/render.py:102-107` |
| P4 | **沒有節流**：馬達 `st_show()` 每幀都送（20ms ⇒ 50 次/秒），即使速度 byte 完全沒變 | `lib/hw/uart_motor.py:575-577` |
| P5 | **共享 buffer 的生命週期陷阱**：`Proto.pack()` 回傳的是共享 buffer 的 view（契約明言下次 pack 會覆蓋），一旦發射變成非同步就會踩雷 | `lib/sys/proto.py:62-72` |
| P6 | **改變硬體時基與發射會互踩**：`bus_speed` 切 baud 前必須先確認 ACK 送完，目前是手動等 `txdone()`，沒有「等某個介面全部送完」的統一入口 | `lib/sys/bus_speed.py:139-150` |
| P7 | **沒有可觀測性**：任何介面都沒有排隊長度／送出數／丟棄數／最大等待時間的統計 | — |
| P8 | **writer 自己阻塞**：例如 MP3 寫完還 `sleep_ms(15)`，阻塞發生在呼叫端 task 的上下文，中心無法統籌 | `lib/hw/mp3_tf_16p.py:69-71` |

### 2.2 已經實際踩到的坑

- **電機 UART 洪水**：舊版停止分支每個 runner 週期都推一帧完整中性幀，把電機 UART 灌爆（`doc/03_notes/01_changelog.md:348-351`，已局部修掉，但同樣的坑對任何新 writer 都還在）。
- **NC4 掉包**：夜測確認 `CircuitTask` 要跟 network / log / render 等搶 core0，rxbuf 溢位 → CRC 壞 → 丟幀，速度越高掉越多（`doc/03_notes/08_night_test_results.md:252, 312, 555`）。
- **同一條線兩種協議的物理風險**：UART-412 的 ATtiny412 是軟體 UART、無 CRC、任何下降緣就取樣（`UART-412/UART-412.ino`），在 NC4 流量下會誤判 → 目前只能靠「分線」避開（`ports/S3/ESP32-S3-1_18/README.md` 的實測成功組合），軟體層沒有防護。

### 2.3 這些問題的共同根源

「**誰可以什麼時候寫哪個硬體**」這件事**沒有單一決策點**：

- 每個模組自己決定何時寫、寫多少、要不要重試；
- 沒有地方知道「現在有別人在同一條線上排隊」；
- 今天不出事，只是因為**剛好同核**（合作式排程天然序列化）與**剛好用不同實體線**這兩個隱性假設還成立——config 一改就會破。

## 3. 想解決什麼問題

1. **競爭**：同一條匯流排被多個模組同時寫入（位元組交錯、協議互踩、誰先誰後靠運氣）。
2. **無序**：重要且不可丟的（NC4 回覆）與大量可丟的（幀）混在一起，沒有輕重之分。
3. **無節制**：不需要送的時候還在送（每幀重送相同內容），白白佔用線路與 CPU。
4. **不可見**：出問題時看不出是「排隊太長、被丟掉、還是寫太慢」。
5. **不可擴充**：每加一種輸出或一個外設，就要再散一個新的發射點到某個 task 裡，既有模組的發射邏輯也跟著被改動。

---

## 4. 目標

**總目標：所有對外發射集中到單一渲染／輸出模組，由它統一控制所有外圍硬體。**

| # | 目標 | 達成時的樣貌 |
|---|---|---|
| G1 | **每個實體介面只有一個 writer** | 任何時刻，一條線／一個外設只有一個地方在寫；其他模組只能「交出去」，不能自己動手 |
| G2 | **集中決策** | 「什麼時候可以寫哪個介面、先寫誰、要不要合併、要不要丟」全部在一處決定，不散落在各 task |
| G3 | **輕重有別** | 不可丟的（NC4 回覆）不被可丟的（幀）拖累；不同介面有明確的先後與節奏 |
| G4 | **不做白工** | 內容沒變就不發；送不出去的舊資料該丟就丟，不排隊等死 |
| G5 | **可觀測** | 每個介面都看得到：目前排了多少、送了多少、丟了多少、等最久多久 |
| G6 | **可擴充** | 新增一種輸出／一個外設時，只註冊進中心，不必改動既有模組的發射路徑 |
| G7 | **不犧牲即時性與記憶體** | 熱路徑零額外配置；NC4 回覆延遲不變差、不掉幀；不因集中化而拖慢 core0 |

> 註：G1~G7 是「要達成什麼」，**不含任何實作方式**（怎麼排隊、怎麼分優先級、放哪一核、用什麼資料結構，全部留待日後設計）。

---

## 5. 非目標（現階段明確不做）

- 不改 NC4 協議本體、不改各 driver 內部的時序（DE 切換、DMA 分 chunk 等）。
- 不追求「一條線跑多種 baud」——那是硬體限制（UART-412 固件寫死 9600），不是軟體能解的。
- 不改動 pixel 效果、音訊合成等「計算」邏輯；本計劃只管「發射」。
- 不為了集中化而新增阻塞點：現行的即時性與幀率是底線。

## 6. 範圍：現在有哪些「發射」要納入

| 介面 | 現在的發射者（位置） | 特性 |
|---|---|---|
| NC4 回覆（circuit UART） | `tasks/bus_decode.py` → `ctx["send"]` → `lib/sys/circuit_bus.py:126-158` | 不可丟，stop-and-wait |
| NC4 回覆（WS / TCP / UDP） | `lib/sys/net_bus.py:429-458` | 不可丟 |
| NC4 回覆（ESP-NOW） | `lib/sys/now_bus.py:108-137` | 可合併 |
| 像素幀（WS2812 / APA102 / PCA9685） | `tasks/render.py:102-107` → `lib/sw/PixelController.py:144-154` | 可丟，50fps |
| 馬達（UART-412） | `lib/hw/uart_motor.py:575-577`（經 PixelStreamer） | 可丟／可合併，內容不變不需重送 |
| 顯示 5-byte（UART） | `tasks/action_task_1.py:388-402` | 可丟，事件驅動 |
| MP3-TF-16P（UART） | `lib/hw/mp3_tf_16p.py:69-71` | 可丟，writer 內含阻塞 |
| 音訊（I2S DAC） | `tasks/audio_player_task.py:96-165` | 不可丟，長阻塞、時序敏感 |
| LCD / SPI | `tasks/lvgl_task.py`、`lib/sys/bus_adapter.py` | 可丟，**只能 core0** |
| SD 卡 | `lib/sys/fast_io.py`（已有 `_sd_lock`） | 不可丟，兩核共用 |
| 日誌（USB REPL） | `tasks/log_task.py` | 可丟，低優先 |

# 14 — P4 (RISC-V) viper `ptr16` 讀 PCM 當無號數 → 拆聲爆音（已修）

> **狀態**：✅ 已修復並實機驗證（ESP32-P4 / ESP32-P4-ETH_mp3）
> **日期**：2026-09
> **檔案**：`ports/P4/ESP32-P4-ETH_mp3/tasks/dj_task.py`（混音器 `_mix1`~`_mix4`）
> **一句話**：P4 的 MicroPython viper `ptr16` 把 s16 PCM 樣本當「無號數」讀，
> 負樣本全變超大正數 → 波形被整流 → 只要音量一衰減就拆聲爆音。
> 解法是改用 `ptr8` 逐 byte 組回並還原 sign。

---

## 1. 症狀（用戶回報）

- 播放 WAV 音效「嚴重拆聲 / 爆音」。
- 音量調低 → 「清晰了一點但**仍然太大聲爆音**」；音量越低反而越裂。
- 某些實驗（接近滿音量 / 特定檔案）可以「清晰播放」→ 讓人不斷懷疑是轉檔問題，
  但**檔案層交叉驗證全部正確**（見 §5）。

---

## 2. 根因

16-bit PCM 每個樣本在記憶體是 2 bytes，同一串 bit 有兩種解讀：

| 記憶體 bit | 無號數 (0..65535) | 有號數 (-32768..32767) |
|---|---|---|
| `1111 1111 1001 1100` | 65436 | **-100** |

喇叭要正確出聲，-100 必須被讀成 -100（聲波下半週）。但 **ESP32-P4（RISC-V）的
MicroPython viper `ptr16` 讀取是無號語意** → 負樣本被讀成 `65536-x` 的大正數。

混音公式 `s = sample * gain >> 15` 在 gain<1（音量衰減）時：

```
-100 讀成 65436，×0.25 = 16359  →  輸出巨大正數（不是 -25）
```

→ 負半週全部被「整流」成大的正輸出 → 波形變全正半週鋸齒 → 拆聲。
**gain=1.0（滿音量直通）時，無號讀取「繞一圈」剛好等於原值，聽起來正常**——
這就是「某些實驗清晰」的真正原因，也解釋了「調低音量反而更爆」。

## 4. 修正內容

四個 viper 混音器（`_mix1`/`_mix2`/`_mix3`/`_mix4`）由 `ptr16` 改為 `ptr8`
逐 byte 組回 s16：

```python
@micropython.viper
def _mix1(out, a, ga: int, lim: int, n: int):
    po = ptr8(out)
    pa = ptr8(a)
    for i in range(n):
        v = int(pa[i * 2]) | (int(pa[i * 2 + 1]) << 8)
        if v > 32767:
            v -= 65536            # 還原 sign
        s = v * ga >> 15
        if s > lim:
            s = lim + ((s - lim) >> 2)
        elif s < -lim:
            s = (-lim) + ((s + lim) >> 2)
        po[i * 2] = s & 0xFF
        po[i * 2 + 1] = (s >> 8) & 0xFF
```

關鍵只有三行：**低 byte | 高 byte<<8 → 超過 32767 就減 65536**。輸出側一樣用
`ptr8` 分兩 byte 寫回。實測 44.1kHz×2 速度足夠（P4 @360MHz）。

> 不要寫回 `ptr16` 做輸出存取 —— 除非先確認該目標的 viper ptr16 是有號語意
> （ESP32-S3 / Xtensa 上是，P4 / RISC-V 上不是）。

## 5. 為何「格式 / 轉檔」不是元兇（交叉驗證記錄）

破音發生時的第一直覺是轉檔，以下驗證全數排除：

- `.mpeg`（實為 48kHz/192k MP3）→ WAV 用 **Apple afconvert** 轉出 44.1k，
  與 SD 上既有 WAV **逐 byte 相同**（MD5 一致）。
- **ffmpeg 9.0.1** 重轉結果與開源解碼器 miniaudio 完全一致；
  與既有 WAV 差在 encoder priming（±25ms 對齊 / 約 0.86× 振幅），內容正確。
- 兩版 WAV 削波率都 <0.12%（母帶本身輕微過載，非轉檔造成）。
- E 開頭約 33 秒是「近無聲漸進導引段」，聽感像壞檔，實為原始內容。

**結論：這條專案的 WAV 轉檔（44.1kHz/16bit/立體聲）是對的，破音在韌體讀取。**
